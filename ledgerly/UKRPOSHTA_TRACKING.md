# Автотрекінг Укрпошти через Parse.bot

Договір та API-ключ Укрпошти не використовуються. Потрібен власний ключ Parse.bot.

## Підключення

1. Зареєструйся в [Parse.bot](https://parse.bot/pricing). Для безкоштовного старту картка не потрібна.
2. Відкрий [Ukrposhta API](https://parse.bot/marketplace/c10d653e-b6d5-4a07-b4ea-81a421befd05/track-ukrposhta-ua-api)
   та натисни Subscribe, якщо сервіс цього вимагає.
3. Settings → Account → API Keys → Create API Key. Збережи ключ у себе — він показується один раз.
4. Відкрий **Налаштувати Укрпошту.command**, встав ключ прихованим введенням.
5. Перезапусти Ledgerly. Сам Repliq і налаштування mono не змінюються.

Ключ зберігається в `private/ukrposhta.json`, права 600. Нікому не надсилай цей файл.
Перед зміною є приватна резервна копія `private/ukrposhta-backup.json`.
Якщо користуєшся власною копією API в Parse.bot, її UUID можна поставити в `scraper_id`.
Повна URL-адреса не приймається: ключ відправляється тільки на api.parse.bot.

## Власнику

Додавай ТТН у звичну тему відправлення. Номери Укрпошти: 13 цифр або міжнародний
формат на кшталт `RR123456789UA`. Вони потрапляють у тему автотрекінгу замість ручної.
Укрпошта й Нова пошта використовують одну спільну тему трекінгу. Окрема тема
«Укрпошта» та параметр `TG_MANUAL_THREAD_ID` більше не потрібні для роботи.
Після підключення також перевіряються незавершені записи ручного трекінгу за останні
45 днів. Замовлення, які вже позначені отриманими, скасованими або поверненими,
автоматично заново не відкриваються.

При зміні статусу оновлюється та сама картка. Підтверджене вручення оновлює замовлення
та передається у звичний облік/1С. У картках зазначена Укрпошта. Статус перевізника
не підтверджує отримання післяплати на банківський рахунок.

Невідомий статус, відсутня посилка, порожній результат і збій API ніколи не означають
отримання. Для вручення потрібна явна подія, час і прив'язка до правильної ТТН.
Старіша подія не перезаписує новішу. Повернення відправнику не вважається продажем.
Історичне вручення, старше за дату створення запису більш ніж на 45 днів, не
проводиться в обліку автоматично — це потребує перевірки відповідності ТТН.
Коли Telegram недоступний, статус кешується і повідомлення повторюється без нового
платного запиту. Збережені статуси можна переглядати без витрати кредитів.

## Частота й безкоштовний бюджет

Пакет містить до 30 активних ТТН. Для 1–30 одночасних відправлень перевірка орієнтовно
раз на 6 годин: до 124 пакетних викликів за 31 день. Для 31–60 інтервал одного
повного обходу збільшується до 12 годин, для 61–90 — до 18, для 91–120 — до доби.
Так навіть більша кількість одночасних посилок не множить витрати пропорційно.
100 відправлень за місяць не означає 100 одночасно активних посилок.

Готовий endpoint заявляє 1 кредит за успішний пакетний виклик. Локальний лічильник
враховує кожну спробу, включно з невідомим результатом: це консервативний захист.
Початкові обмеження — 160 спроб за календарний місяць і 180 загалом. Лічильники
живуть у базі та не скидаються після перезапуску або заміни ключа.
Платних поповнень, автоматичних підписок чи покупки кредитів у коді немає.

На сторінці marketplace написано про 200 кредитів/місяць, а загальна сторінка тарифів
говорить про 200 безкоштовних кредитів без чіткої обіцянки щомісячного поновлення.
Тому **не розраховуй на нескінченний безкоштовний трекінг**: звір поновлення та
залишок у своєму кабінеті. Після безкоштовного ліміту потрібне явне рішення власника;
код призупинить запити та повідомить адміністратора. В `total_limit` можна поставити
підтверджений доступний загальний бюджет; не збільшуй його на припущенні.

## Межі перевірки

09.11.2026 виконано один реальний пакетний запит із двома ТТН: Parse.bot повернув
HTTP 200 та окремі події з номерами відправлень. Перевірено структуру зі списком
подій, де кожен елемент містить `barcode`. Одна подія означала онлайн-реєстрацію
без фізичного приймання, друга — історичне вручення. Створена онлайн накладна
показується як «Очікує приймання» й не позначає замовлення відправленим.

Запит не змінював замовлень або обліку. Окремі офлайн-перевірки покривають
доставку, повернення, повтори, помилки сервісу, спільну тему та старі події.
Робота стороннього сервісу в майбутньому не гарантована. Якщо формат відповіді
зміниться, автоматичний облік не вгадуватиме результат, а проситиме перевірку.
