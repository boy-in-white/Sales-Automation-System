# Розбір реальних запитань покупців OLX

Вивантажено всі 301 доступний діалог: 1 716 вхідних повідомлень. Для аналізу
підтверджено 296 діалогів за власними оголошеннями. Решта 5 не використана
як приклади покупців, оскільки належність оголошення не підтвердилась.

У підтверджених діалогах: 1 644 текстових повідомлення покупців, 1 390
унікальних текстів, 30 повідомлень лише з вкладеннями та 27 службових
повідомлень OLX. Вкладення не завантажувались. Тексти відповідей продавця
не зберігались і не використовувались як зразки відповідей чи джерело фактів.

Серед позицій є Suvene, Gallery Dept, Broken Planet, інший одяг і телефони.
Із цих чатів взято способи формулювання запитань. Характеристики, ціни,
наявність та домовленості щодо інших речей не переносяться на поточні товари.

## Що змінилося

| Тип повідомлення | Поведінка |
| --- | --- |
| «Маєте ску?», «розмер», «черниые», помилки в слові «післяплата» | Відомі скорочення й помилки розпізнаються, оригінальний текст і дані доставки зберігаються без виправлення |
| «Фіолетовий», інший відсутній колір | Перевіряється саме вибраний розмір і кількість; пропонуються тільки наявні варіанти |
| «M або L», «сірі чи чорні» | Бот уточнює вибір, не обирає останнє слово за клієнта; вже відомі розмір і колір зберігаються |
| Нуль, дроби, від’ємна або величезна кількість | Замовлення не змінюється, запитується коректна кількість; перевірка працює й для кількох позицій |
| «Післяплата», «накладним», «оплата у відділенні» | Розпізнається спосіб оплати; відсутність передоплати не обіцяється |
| «100 грн через OLX?», «по пп» | Пояснюється різниця способів або уточнюється сума, без вгадування |
| «Передоплату віднімете?», «скільки на пошті?» | Відповідь розраховується зі збереженого рахунку; доставка вказується окремо |
| «Скинув», «прийшли?» | Повідомлення клієнта не стає підтвердженням надходження коштів; повторний переказ не запитується |
| Колір/розмір після виставлення рахунку | Не записується як місто, ПІБ чи адреса; збережений рахунок не підміняється |
| «Скидайте реквізити» | Не плутається зі знижкою; використовується чинний рахунок |
| «За 600 віддасте?» | Застосовується правило магазину щодо торгу, ціна з повідомлення клієнта не підставляється в рахунок |
| «Скільки доставка?» | Не підміняється ціною товару; тариф визначає перевізник |
| «Встигне до суботи?», «о котрій відправите?» | Планова відправка відокремлена від прибуття; непідтверджена година не обіцяється |
| «Який розмір на людині на фото?» | Не перетворюється на вибір розміру або параметри покупця |
| «А кофти Suvene?», інша марка | Не видаються характеристики чи залишки рекламованих штанів за іншу річ |
| Відгук, дефект, подяка, «я подумаю» | Відгуки відрізняються від звичайної подяки; проблема з отриманою річчю — від запиту про її властивості |
| «У вас придбали товар з OLX Доставкою…» | Службове повідомлення не вважається реплікою покупця або перевіреною оплатою |

## Стиль розмови

Вітання підлаштовується під клієнта: «Добрий вечір», «Доброго ранку»,
«Привіт», «Салам» тощо. У продовженні діалогу назва товару не повторюється
без потреби. Технічні подробиці не додаються до звичайної консультації.
На пряме запитання про бота залишається чесна відповідь про Repliq.

## Які факти можна доповнити

У `shop.json`, усередині `products[].facts`, для кожної моделі окремо
доступні необов’язкові текстові поля (до 400 символів):

- `tags` — чи є бірки та які саме;
- `density` — щільність тканини / вага виробу, якщо відомі;
- `care` — правила прання, прасування, догляд за декором;
- `package` — комплектація й упаковка;
- `photo_model` — які розмір і параметри людини на фото.

У `shop.json → shop` можна додати необов’язкові текстові поля:

- `pickup` — умови самовивозу або зустрічі;
- `dispatch_city` — місто відправлення;
- `delivery_cost` — опис умов оплати доставки, якщо стандартного пояснення недостатньо.

Ім’я отримувача переказу береться з `private/payments.json → recipient`.
Необов’язкове `private/payments.json → bank_name` задає назву банку для
запитань на кшталт «Приват чи моно?»; за номером картки вона не вгадується.
Умови повернення для повної передоплати та передоплати 100 грн уже задані
окремо; актуальна інструкція — DELIVERY_MONITOR.md.
Без підтверджених даних бот не вигадує бірки, GSM, параметри моделі
або дату нового надходження. Для невідомих фактів,
які потребують особистої відповіді, використовується наявний механізм допомоги.

## Перевірка й зберігання

Окремо переглянуто повні сценарії: вибір → недоступний колір → інший колір;
післяплата → сума до отримання → повідомлення про оплату; зміна варіанта
під час збору адреси; неоднозначні й неможливі значення; привітання та чесна
відповідь про автоматизованого помічника.

На текстах актуальних моделей виконано 8 934 ізольовані проходи через різні
стани діалогу: без падінь, зміни вхідної пам’яті або самостійного підтвердження
оплати. У цих перевірках використовувались умовні залишки й реквізити.

Приватний експорт лежить у `private/research/2026-11-08/` з правами 700/600
і виключений із Git. Він не завантажується робочим ботом: у роботі залишилися
тільки невеликі правила розпізнавання. Спільний SQL Ledgerly не змінювався.

Повторний експорт — `tools/export_customer_questions.py` з явними
`--data-dir`, `--output` і, за потреби, `--limit` (до 1500 діалогів).
Утиліта дозволяє лише читання API та поновлення вже наявного доступу.
